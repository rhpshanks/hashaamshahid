Case study 01

A two-hour daily job that now takes five minutes

Miqyas reads Pakistani news every morning, writes an original summary of each story, scores its likely impact, and publishes a live website — with no daily work from me. I designed the system, directed the AI tools that built it, and set it up to maintain itself.

The problem worth solving

There is too much news and too little time. A headline rarely tells you how much a story matters to your money, your government, or your daily life. The reader has to open ten articles to find the two that affect them.

Producing something that answers that daily is the expensive part. Reading every source, spotting which outlets are covering the same event, writing an original summary of each story, judging its impact, publishing, and confirming the update actually went live — that is over two hours of work, every single day, and it is mostly judgement rather than typing. Miss a day and the product is dead.

Why this is the right shape for automation. The task is genuinely daily, it is mostly judgement, and it is expensive precisely because a person has to be there for it. That is the same shape as most of the back-office work I automate for businesses — the difference is only the subject matter.

What it does

Every headline card carries an AI-written summary in its own words, never copied text, alongside a link to the original story. Three impact badges — economic, political and social — each read positive, neutral or negative. Market relevance and confidence are shown as high, medium or low.

  • Duplicate coverage merges. When several outlets cover the same event, they collapse into one card with links to each.
  • Every colour has a matching shape — circle, triangle, square — so the signals work for colour-blind readers.
  • Political lean is shown without colour and names no party. Painting one side green and the other red would itself be a statement.
  • Around the cards sit a trend chart, search, date filters, topic following, a methodology page, a weekly roundup and a public track record.

Decisions I made, and one I talked myself out of

I first considered an indicator showing which party's supporters would like a story, then rejected it. The shipped alternative uses soft labels, names no party and carries no colour. In a Pakistani news context, an indicator like that would have read as taking a side no matter how carefully it was calculated — and the product's whole value rests on not appearing to.

Trust is earned by being open about method. So a methodology page explains exactly how the readings are produced, every badge has a "report this reading" action, risky stories are flagged for review by rule, and a public track-record page shows the AI's own statistics — including how often it is unsure.

How I built it

01 / SPECIFICATION

Write it down before building anything

A technical document covering the platform choice, the six-indicator model, the visual palette, accessibility rules and editorial safeguards. Constraints on accuracy, neutrality and compliance were set before any code existed.

02 / INTERFACE

A phone-first reading surface

React with Vite, built on design tokens and reusable components, light and dark themes, and a hand-built SVG trend chart with hover and touch tooltips.

03 / THE PIPELINE

A scheduled agent, no server to run

Every morning at 9 AM Pakistan time it reads the sources' RSS feeds, checks each site's crawling rules permit it, reads and merges same-event coverage, writes original summaries, scores the indicators, attributes security claims to their stated source rather than presenting them as verified, flags stories for human review by rule, saves the day's data and pushes it.

04 / DEPLOYMENT

Publishing that needs no human

Each push triggers a deployment, so the live site updates itself. A second agent runs weekly and writes an original roundup from the site's own accumulated data.

05 / SCALE

Built for an archive that keeps growing

One data file per day, loaded page by page as the reader scrolls, with only the newest refreshed and older ones cached. Long lists render only what is on screen, so speed holds as the archive grows.

06 / VERIFICATION

Never trust the first answer

Every change was tested in a real browser. That caught a list silently rendering zero cards, a chart label that dropped out twice where the first fix had only treated the symptom, duplicate IDs across days, duplicated headlines in the archive, and a one-day tally error found by recomputing totals from the raw data.

The decision I am most pleased with

Asked to backfill history so the archive looked fuller, I checked the sources' crawling rules, found no compliant way to get real past headlines, and let real history accumulate instead of inventing any. A product whose entire claim is trustworthy readings cannot open with fabricated data.

How I direct AI tools

My job was deciding what to build, why, and what "correct" means. The AI's job was execution, which I then checked. In practice that means four habits:

  • Instructions as specifications. The daily agent runs from a written task file with the edge cases handled: same-day reruns merge rather than replace, never fabricate detail, never touch another day's files.
  • Design for safe reruns. Automation you can run twice without damage is automation you can trust unattended.
  • Ask for options, decide myself. I had the AI lay out trade-offs — data architecture, palettes, native app versus wrapper — and made the calls.
  • Keep the guardrails inside the process. Compliance checks, review flags and public documentation are part of the automation, not a promise around it.

An operations lesson that paid off

After one push, the deployment didn't happen. Because each link in the chain could be checked separately — the commit visible in version control, the deployment list checked directly — I isolated the fault to the deployment trigger in minutes instead of guessing at it. Systems you can inspect one piece at a time are systems you can fix under pressure.

Honest limitations

  • The readings are AI-generated and can be wrong. The track-record page exists so that is visible rather than hidden.
  • The "report this reading" action currently confirms in the interface only — there is no review queue behind it yet.
  • The daily-digest signup is a preview and stores nothing on a server.
  • Next: a real email digest, and a proper report-review workflow.

What this demonstrates

Process mapping, specification writing, AI-directed development, scheduled automation, deployment pipelines, data-architecture thinking, quality verification, compliance awareness — and the part that matters most commercially: turning a repeating manual job into a system that runs without the person who built it.
